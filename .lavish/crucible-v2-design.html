Seven ideas, composable: 1 · Failures float, green folds — all-pass suites collapse to one counted row; failing branches auto-expand. 5,214 tests → ~12 visible rows. 2 · Heat-strip minimap — one cell per test; the whole run in one glance strip; click jumps. 3 · Failure digest — identical assertion messages dedupe into groups ("+3 identical") so one root cause isn't 40 rows. 4 · Virtualized tree — only visible rows exist in the DOM (~40 nodes for 10k tests). 5 · Progressive payload — GET /api/v2/events/<id> returns suite-level summaries first; leaf pages fetch on expand, so a 10k-test tree never ships whole. 6 · Filter bar — status chips, free-text, module/crate facet — same controls agents get as query params. 7 · Density toggle — comfortable / compact / ultra (suite-per-line). Annotate the ones you want in the first UI wave.

Resolved this round + still open

Open items

  • Run context — DECIDED ✅ with graceful degradation. Ingest events accept an optional context block: git {branch, commit}, wave, orchestrator (mainline | track-N) — so in Model-B projects a track's check-run and Mainline's regression are distinguishable on the same timeline and traceable to the exact commit. Every field is optional: lightweight projects (no waves, no tracks) send nothing and the API and UI degrade gracefully — cards simply omit the badges. The server never requires context it wasn't given.
  • Retention — DECIDED ✅. Default: last 100 runs full-fidelity per project; older runs roll up into aggregates. Where wave context exists, rollups are per wave (a wave's cycle history stays reconstructable); without it, daily buckets. Per-project override stays available.
  • TOON pinning — explained. The choice: (a) vendor the reference implementation — the official TypeScript serializer from toonformat.dev, copied into the repo like van.js. Pro: spec-exact as TOON evolves, handles every edge (nested tables, quoting). Con: ~more code than we use, upstream churn to track. (b) pin our subset — implement only what Crucible responses emit (scalars, key:value, uniform tables, help lists), document it as "Crucible TOON", freeze it. Pro: ~150 lines we fully own, zero upstream risk. Con: if an agent-side TOON parser follows the full spec and we drift, mismatch. Recommendation: (b) pin the subset — our consumers are our own upgraded scripts + CLI, so both ends are ours; spec-tracking buys nothing today and the subset is documentable in ten lines. Revisit only if third-party TOON tooling enters the picture.
  • Still open: which density-playbook ideas (F4½) make the first UI wave — annotate them; and anything else the storyboard gets wrong.
