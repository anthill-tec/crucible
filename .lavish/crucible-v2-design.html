Section 1

Architecture — what talks to what?

One Bun process serves three audiences: the legacy client fleet (JSON, byte-compatible), agent-facing AXI surfaces (TOON + hints), and the human dashboard (VanJS/VanX/VanUI SPA over SSE).

The agent lifecycle v1 modeled implicitly (registration == first heartbeat) becomes explicit in v2 — register and unregister are first-class verbs, while heartbeat keeps its upsert behavior so old clients lose nothing. Two refinements from your whiteboard: every agent API call is an implicit heartbeat — an agent busy ingesting runs never needs a dedicated ping; explicit heartbeats only fill silent stretches (long compiles, thinking time). And the decay thresholds are configurable — server-wide defaults (60s/300s/1h), overridable per project. Agents that fail to unregister decay to tombstoned — kept visible (greyed, with last message and time-of-death) so a crashed agent is a diagnosable fact, not a silent disappearance — then pruned:

Server health is part of the contract too

v1 monitored the backend itself and the frontend surfaced it. v2 keeps that: GET /api/health (uptime, version, snapshot-write status, project/agent/event counts) plus SSE keep-alive frames every 15 s. The SPA pins a status pill in the top bar — ● crucible healthy flips to ● backend unreachable when keep-alives stop AND a health probe fails, and all "live" data visibly greys rather than silently going stale. Agents get the same signal: every AXI response echoes server: healthy · up 4h12m, and orchestrator scripts can gate on /api/health before dispatching a wave.

⚗ Codec translation layer new — from review feedback

v1's parsing was JUnit-spined, and it showed: tools that don't speak the JUnit standard were shoehorned in awkwardly, and the BDD/Playwright runtime was never fully realized. v2 inverts this: a codec registry where every test tool gets a first-class codec that translates its native output into one canonical RunSchema — JUnit becomes just one codec among many, not the spine.

  • Canonical RunSchema — summary + suite/case tree + coverage + compile diagnostics, tool-agnostic. Every event stores it, plus stack (rust/java/py/ts/…), codec (junit/nextest/playwright/…) and tool version.
  • Failure detail preserved — v1 trees carried only name/status/duration; v2 leaves carry failure: {message, type, trace} from the tool output, so the UI can show the actual assertion message and stack trace of every failed test (see run drill-in, §4).
  • Codecs, not parsers — junit, rustc, javac, python, tsc (v1 parity) + playwright (JSON reporter: features → scenarios → steps, browser, trace links), vitest, TAP. Adding a stack = adding a codec, no core changes.
  • Stack-aware UI — the dashboard renders by codec: a nextest run shows crate→suite trees; a Playwright run shows feature→scenario→step with browser badges and trace links; a bare TAP stream still gets a sane generic view. The UI can always tell you what kind of run it's looking at.
  • BDD finally first-class — frontend projects get the BDD axis as designed (not bolted on): Playwright/Vitest codecs, scenario-level pass/fail, and the unit|bdd ingest-state split v1 only stubbed.
Section 2

The agent experience, worked backwards

Today an agent talks to Crucible through copy-pasted urllib helpers and gets {"ok": true} back — no orientation, no guidance, no confirmation of what changed. The *-axi tool family (gh-axi, lavish-axi, chrome-devtools-axi) proved a better idiom set. Applied to Crucible:

AXI idiomIn Crucible v2
Dashboard-firstGET /api with no args → orientation: service info, project list, your agent's state, suggested next calls. An agent landing cold knows what to do.
help[N]: hintsEvery response ends with contextual next steps. After register → "ingest your first run". After a failing ingest → "re-run & re-ingest; RED→GREEN must show as two events".
TOON outputToken-efficient responses for agent readers via content negotiation (Accept: text/toon or ?fmt=toon). JSON stays the default — v1 fleet + SPA unaffected. See §3.
Idempotent mutations that report what changedchanged: true|false on every write. Re-running a failed ingest is safe and says so. projects/add on an existing key stops being an ignored 400 — it reports changed: false (v1 path still 400s for compat).
Explicit verbsPOST /api/agents/register and /api/agents/unregister — the lifecycle v1 buried in heartbeat/remove becomes discoverable. Old endpoints remain as aliases forever.
Token-frugal truncationBig payloads (compile error walls, 1000-case trees) come back summarized with a full: /api/events/<id>?fmt=json pointer instead of flooding the agent's context.

Cost of the AXI layer: a TOON serializer (~150 lines, zero deps), content negotiation, and hint-authoring per endpoint. No new process, no client changes required — legacy JSON is untouched.

Where should AXI live? Your whiteboard note proposes a different split: the backend focuses on a clean v2 API (using the old one as reference, not as a byte-frozen contract), while AXI adherence is implemented in the client python scripts — which are fully ours to upgrade. That trades zero-day compat for a quirk-free API. Now decision Q6.

Section 3

TOON as the agent wire format

TOON (toonformat.dev) is a token-oriented notation: objects as key: value lines, uniform arrays as name[N]{cols}: tables. It shines exactly where Crucible's reads are heaviest — event lists, agent lists, test trees. The same 3 events:

 {"id":"evt-1783440723001-7","agentId":"CR-NAI-042-RED",
  "kind":"test","tier":"unit","timestamp":1783440723001,
  "summary":{"total":5,"passed":2,"failed":3,"pending":0}},
 {"id":"evt-1783440899412-8","agentId":"CR-NAI-042-GREEN",
  "kind":"test","tier":"unit","timestamp":1783440899412,
  "summary":{"total":5,"passed":5,"failed":0,"pending":0}},
 {"id":"evt-1783441002110-9","agentId":"verify-nai-042",
  "kind":"test","tier":"regression","timestamp":1783441002110,
  "summary":{"total":214,"passed":214,"failed":0,"pending":0}}]}
TOON — ~140 tokens*
ok: true
events[3]{id,agent,kind,tier,total,passed,failed}:
  evt-1783440723001-7,CR-NAI-042-RED,test,unit,5,2,3

Section 4

Dashboard concepts DECIDED Q1: A + B hybrid

Decided: Mission Control (A) is the home — cross-project cockpit; clicking a project drills into its workspace (B) with tabs for Runs / Agents / Coverage / Compile / BDD. Concept C (a single filterable live feed of every event with a pinned inspector) was the third philosophy — not chosen as the backbone, but its inspector idea survives as the run drill-in:

🔍 Run drill-in — seeing the actual tests and errors

Every run card opens (click / Enter) into the full run detail: the suite→test tree with per-test status and duration; each failed test expands to its assertion message and stack trace (preserved by the codec via failure: {message, type, trace} — v1 never stored these); compile events show per-file structured errors with the raw output one toggle away. In the A+B hybrid this renders as a slide-over panel on the Mission Control timeline and as the Runs tab's detail view inside a project workspace.

The mocks below are faithful scaffolds — every element maps to reconstructed data. Styling ships as the forge palette expressed as a custom DaisyUI theme (Q5).

Section 5

Design language — "forge" tokens color scheme approved

This page is rendered in the proposed system itself: deep-charcoal surfaces, one molten accent, mono-forward data typography, status colors reserved for status. Per Q5, these tokens ship as a custom DaisyUI theme (--color-primary: #ff7a1a etc.), so DaisyUI components arrive pre-skinned in forge.

🔬 What Lavish actually runs on examined via opensrc

Pulled kunchenguid/lavish-axi@main and read the source: artifact pages get Tailwind 4 browser runtime + DaisyUI 5 (classes compile in-browser — no build step); the editor chrome itself is vanilla JS (chrome-client.js) — React 18 appears only as an Excalidraw dependency for whiteboards; Express 5 serves it. Crucible v2 adopts the same environment on Bun: @tailwindcss/browser + daisyui vendored, VanJS + VanX as the reactive layer driving DaisyUI-classed DOM — the decided Q5 hybrid, and philosophically identical to how Lavish itself is built.

Section 6

Risks & open questions

  • Compat regressions — the v1 contract has quirks (top-level displayName ignored, 400-on-duplicate projects/add, coverage-discard-on-fail). Mitigation: the compat surface gets contract tests derived line-by-line from the DN before any AXI work starts.
  • TOON drift — hand-rolled serializer vs the evolving spec. Mitigation: vendor the reference TS implementation (zero-dep) or pin our subset (tables + scalars + help lists) and document it.
  • Component depth — resolved by Q5: DaisyUI supplies the widget library (stats, timelines, badges, drawers); VanJS/VanX renders it. Only the virtualized suite tree stays hand-rolled (~100 lines with VanX reactivity).
  • Liveness without pings — resolved: run/API activity IS the heartbeat (no dedicated ping loop), so there is no heartbeat noise to filter; the stream shows runs, liveness derives from activity.
  • Tiers & test approaches — resolved: upgraded clients send tier so the UI can represent them differently. unit / module / integration share the same tools per stack; e2e is a different approach; BDD applies only to UI applications — and for those, Crucible itself can harness the run (execute Playwright on the agent's behalf), a later-wave capability now in the PRD. Git branch/commit per ingest stays open.
